## ۲) یافته‌های کلیدی تحقیق (هیدی‌فای ۱۴)

### ۲٫۱ احراز هویت

هدر درخواست:

```
Hiddify-API-Key: <uuid ادمین>        # یا یوزرنیم/پسورد ادمین (Basic)
```

مسیر پایه (به `<admin_proxy_path>` از «تنظیمات ← تنظیمات خیلی پیشرفته ← مسیر پروکسی مدیران» نیاز دارید):

```
https://<domain>/<admin_proxy_path>/api/v2/admin/...
```

مستند تعاملی OpenAPI خود پنل در مسیر `/api/v2/admin/docs` (و `/api/v2/panel/docs`) در دسترس است — بهترین مرجع در زمان توسعه.

> نکته مهم: مسیر API باید همان میزبان/پروکسی‌مسیری باشد که پنل با آن بالا آمده؛ در صورت اشتباه بودن مسیر، پاسخ ۴۰۴/ریدایرکت لاگین برمی‌گردد نه خطای واضح. در اپ باید «تست اتصال» به‌صورت صریح پیاده شود.

### ۲٫۲ اندپوینت‌های تأییدشده (از سورس نسخه ۱۴)

| متد | مسیر | کاربرد | نکته |
|-----|------|--------|------|
| GET | `/api/v2/panel/info/` | نسخه و اطلاعات پنل | تست سلامت اتصال |
| GET | `/api/v2/panel/ping/` | ping | سبک |
| GET | `/api/v2/admin/me/` | اطلاعات ادمین جاری | محدودیت‌ها (max_users و…) |
| GET | `/api/v2/admin/users/` | **لیست غنی کاربران + متادیتا** | بهترین انتخاب برای خواندن |
| POST | `/api/v2/admin/users/` | ساخت کاربر | همان مدل صفحهٔ کاربران پنل |
| GET/PATCH/DELETE | `/api/v2/admin/users/<uuid>/` | جزئیات/ویرایش/حذف | برای کاربران زیرمجموعهٔ ادمین هم کار می‌کند |
| POST | `/api/v2/admin/users/bulk/` | عملیات گروهی | `add_days`, `add_limits`, `reset_usage`, `reset_days`, `enable`, `disable`, `delete` |
| GET | `/api/v2/admin/user/` | لیست سادهٔ کاربران | اگر صفر کاربر باشد **۴۰۴** برمی‌گرداند |
| POST | `/api/v2/admin/user/` | ساخت کاربر (schema قدیمی‌تر) | - |
| GET/PATCH/DELETE | `/api/v2/admin/user/<uuid>/` | جزئیات/ویرایش/حذف | روی کاربران زیرمجموعهٔ ادمین ممکن است **۴۰۳** بدهد |
| GET | `/api/v2/admin/dashboard/` | آمار مصرف/آنلاین | برای ویجت داشبورد |
| GET | `/api/v2/admin/admins/` | درخت ادمین‌ها + آمار | برای گزارش نمایندگان |

**داده‌های مهمی که `GET /api/v2/admin/users/` رایگان برمی‌گرداند** (این را از سورس تأیید کردم):

```
users[]: uuid, name, enable, status(active/no_data/…), current_usage_GB, usage_limit_GB,
         package_days, remaining_days, start_date, expire_date, expire_date, mode,
         days_to_reset, last_reset_time, last_online, owner_uuid, owner_name, tags[], telegram_id
meta:    me_uuid, can_add, read_only, admins[], outbounds[],
         link_domains[]  →  [{domain, label, kind, base: "https://domain/<client_proxy_path>/"}]
```

`link_domains[].base` مستقیماً **لینک اشتراک/پنل کاربر** را می‌سازد:

```
subscription_url = base + "<user_uuid>/"
```

این دقیقاً همان `profile_url` است که پنل خودش در صفحهٔ کاربر می‌سازد. یعنی برای ارسال لینک در پیامک فاکتور، **نیازی به دسترسی به تنظیمات پنل یا محاسبهٔ مسیر کلاینت نیست**.

### ۲٫۳ نکات ریز که اگر ندانید ۲ هفته وقت‌تان را می‌گیرد

1. **معنای «تمدید» در پنل** (از سورس `telegrambot/accounts.py`):
   - تمدید کامل = `start_date = None` + `reset_usage()` (یعنی `last_reset_time = today`, `current_usage_GB = 0`) + `enable = true`. یعنی شمارش روزها از **اولین اتصال بعدی** شروع می‌شود.
   - افزودن روز = `package_days = min(10000, package_days + n)`
   - افزودن حجم = `usage_limit_GB = min(1_000_000, usage_limit_GB + n)`
   - ریست مصرف = `current_usage_GB = 0` + `last_reset_time = today`
   
   این‌ها را می‌توان با `PATCH /user/<uuid>/` یا با `POST /users/bulk/` (اکشن `add_days` / `add_limits` / `reset_usage`) انجام داد. **توصیه: برای تمدید از bulk استفاده کنید** چون هم اتمیک‌تر است و هم رفتارش با خود پنل یکسان است.

2. **هر تغییر کاربر → اجرای `apply_users`:** ساخت/ویرایش/حذف کاربر روی پنل، سرویس‌ها را re-apply می‌کند. یک باگ باز در ۱۴٫۰٫۵ گزارش شده که این کار باعث **قطعی لحظه‌ای اتصال همهٔ کاربران** می‌شود ([issue #5642](https://github.com/hiddify/Hiddify-Manager/issues/5642)). نتیجهٔ عملی برای اپ: عملیات گروهی را **دسته‌ای/با تأخیر** بفرستید، نه حلقه‌ای تک‌تک؛ و در UI عملیات طولانی را با پیشرفت نمایش دهید.

3. **محدودهٔ دسترسی ادمین درختی:** در نسخه‌های ۱۴٫۰٫۰b، ادمین بالادست کاربران زیرمجموعه را در لیست می‌بیند ولی `GET/PATCH/DELETE /admin/user/<uuid>/` روی آن‌ها ۴۰۳ می‌دهد ([issue #5607](https://github.com/hiddify/Hiddify-Manager/issues/5607)). ولی **`/admin/users/` (page API) محدودهٔ درختی را رعایت می‌کند**. پس خواندن از `/users/` و نوشتن از `/users/<uuid>/` و `/users/bulk/` بگذارید تا این باگ شما را نگیرد.

4. **لیست خالی = ۴۰۴:** `GET /api/v2/admin/user/` اگر هیچ کاربری نباشد ۴۰۴ می‌دهد. آن را خطای اتصال تفسیر نکنید.

5. **ناپایداری API بین بیلدهای ۱۴.x:** در نسخه‌های بتا نام فیلد و مسیر عوض شده (مثلاً جابه‌جایی `/admin/user/` و `/admin_user/` برای sync نودها، افزودن `preferred_outbound_slug`, `max_total_usage_GB`, `users_layout`). **یک لایهٔ Adapter + تست قراردادی روی یک پنل واقعی لازم است**؛ نسخهٔ پنل را در `GET /panel/info/` بخوانید و در تنظیمات اپ ذخیره/نمایش دهید.

6. **لینک کوتاه اشتراک** برای پیامک: `/api/v2/user/short/` (با کلید کاربر) لینک کوتاه می‌دهد؛ از سمت ادمین چنین اندپوینتی وجود ندارد. برای پیامک، یا از `base+uuid` استفاده کنید یا سرویس کوتاه‌کنندهٔ خودتان (چون پیامک فارسی گران و طول‌محدود است).

7. **کانال امنیتی:** ارتباط فقط HTTPS؛ گواهی self-signed را به‌صورت سراسری bypass نکنید، فقط pinning/اعتماد اختیاری برای همان دامنه.

## ۳) ارزیابی تک‌تک قابلیت‌ها

### ۳٫۱ حسابداری و حساب دفتری مشتریان

- مدل پیشنهادی: **دفتر تراکنش‌محور (Ledger) + فاکتور** روی یک پایگاه‌دادهٔ محلی (Room/SQLite)، با اصول سادهٔ دفترداری دوطرفه.
- هر رویداد مالی یک «ثبت» (Entry) تغییرناپذیر می‌سازد؛ مانده هرگز ویرایش نمی‌شود بلکه با جمع ثبت‌ها محاسبه می‌شود (اوّلاً audit، ثانیاً گزارش درست).
- گردش‌های لازم: فاکتور (بدهکار مشتری)، پرداخت نقدی/کارت‌به‌کارت/پیامکی (بستانکار)، تخفیف، تعدیل، برگشت/لغو، اعتبار/کیف پول، خرید و هزینه (برای سود و زیان).
- پرداخت جزئی و چند پرداخت برای یک فاکتور باید از روز اول پشتیبانی شود؛ بعداً افزودنش مهاجرت دادهٔ دردناکی دارد.
- اعداد: `Long` ریال. هرگز `Double`/`Float`. تبدیل تومان/ریال در لایهٔ نمایش.

### ۳٫۲ اتصال به پنل هیدی‌فای ۱۴

- کاملاً ممکن و ساده؛ سه ورودی لازم است: `baseUrl`، `adminProxyPath`، `apiKey`.
- «تست اتصال» باید `GET /api/v2/panel/info/` + `GET /api/v2/admin/me/` + `GET /api/v2/admin/users/` را بزند و سه چیز را گزارش دهد: نسخهٔ پنل، نام ادمین، دسترسی نوشتن (`meta.read_only`, `meta.can_add`).
- پشتیبانی از چند پنل/چند ادمین: از ابتدا `panel_id` را در همهٔ جاها داشته باشید (اکثر فروشنده‌ها ۲+ سرور دارند).
- اپ باید در حالت «پنل در دسترس نیست» هم کار کند (دفتر و فاکتور محلی) و صف عملیات (WorkManager + Outbox) داشته باشد.

### ۳٫۳ ساخت هوشمند اکانت + تمدید + صدور فاکتور

جریان درست (Saga کوچک با جبران):

1. کاربر/مشتری انتخاب یا ساخته می‌شود (محلی).
2. «بسته» انتخاب می‌شود (نام، حجم GB، روز، قیمت، تعداد دستگاه/محدودیت‌ها).
3. فاکتور **پیش از** تماس با پنل ساخته و در حالت `pending` ذخیره می‌شود (با کلید Idempotency).
4. `POST /api/v2/admin/users/` (ساخت) یا `POST /api/v2/admin/users/bulk/` با `add_limits` (تمدید).
5. اگر موفق: فاکتور → `issued`، اکانت با `panel_user_uuid` به مشتری/فاکتور لینک می‌شود و لینک اشتراک در فاکتور ثبت می‌شود.
6. اگر ناموفق/تایم‌اوت: فاکتور در `pending` می‌ماند، عملیات در Outbox با وضعیت «نامشخص» ثبت می‌شود و **قبل از تلاش مجدد، وضعیت واقعی از پنل خوانده می‌شود** (چون POST می‌تواند موفق شده باشد و پاسخ نرسیده باشد). این «reconciliation» را جدی بگیرید وگرنه اکانت دوبل/فاکتور دوبل تولید می‌شود.
7. اطلاع‌رسانی: قالب پیامک با متغیرهای `{name} {gb} {days} {price} {link} {invoice_no} {date}`.

نکات UX هوشمندسازی: تمدید با یک کلیک روی ردیف مشتری، محاسبهٔ خودکار روزهای باقی‌مانده/حجم باقی‌مانده، هشدار «۳ روز تا انقضا»، «حجم تمام‌شده»، تمدید دسته‌ای همهٔ منقضی‌ها، و پیشنهاد بسته بر اساس تاریخچهٔ خرید مشتری.

### ۳٫۴ ارسال فاکتور متنی با پیامک

- **اپ به‌تنهایی نمی‌تواند پیامک بفرستد** مگر با سیم‌کارت دستگاه (`SmsManager`) که برای کسب‌وکار غیرحرفه‌ای، پرهزینه و غیرقابل ردیابی است. راه درست: پنل پیامکی با API (کاوه‌نگار، SMS.ir، ملی‌پیامک، فراپیامک، قاصدک).
- نیازمندی‌ها: خط خدماتی/شمارهٔ اختصاصی، **ثبت الگوی پیامک (pattern)** برای فاکتور (اجباری در ایران)، لیست سیاه انصراف، و شمارش اعتبار.
- طول پیامک فارسی: ~۷۰ کاراکتر در هر بخش (UCS-2) → لینک طولانی = چند پیام = چند برابر هزینه. پس یا لینک کوتاه بفرستید یا متن را به ۲ بخش استاندارد بشکنید. در اپ باید «پیش‌نمایش + تعداد بخش + هزینهٔ تخمینی» نمایش داده شود.
- معماری: `SmsGateway` به‌صورت interface با چند پیاده‌سازی (کاوه‌نگار/ SMS.ir/ Test-Mock) + صف ارسال + وضعیت تحویل (delivery report) + تلاش مجدد.
- **مهم:** ارسال پیامک از داخل اپ یعنی کلید API پنل پیامکی روی دستگاه است؛ برای یک اپ تک‌کاربره قابل قبول است، برای تیم فروش نه → بک‌اند (بخش ۴٫۲).

### ۳٫۵ خواندن پیامک بانکی + تطبیق پرداخت (سخت‌ترین بخش)

**فنی:** بله. با `RECEIVE_SMS` (گوش‌دادن زنده) یا `READ_SMS` (خواندن صندوق ورودی) در اپ نصب‌شدهٔ مستقیم، همهٔ پیامک‌های بانکی در دسترس‌اند. (توجه: از اندروید ۴٫۴ به بعد فقط اپ پیش‌فرض پیامک می‌تواند در SMS Provider بنویسد، ولی **دریافت/خواندن** برای اپ sideload با مجوز runtime کار می‌کند.)

**اما سیاست Google Play:** مجوزهای گروه SMS فقط برای «اپ پیش‌فرض پیامک» یا «دسته‌های استثنای تأییدشده» مجاز است؛ در فهرست استثناها «SMS-based financial transactions» فقط برای اپ‌های مالی/بانکی و تراکنش‌های پرداخت (مثل UPI) است و اپ حسابداری فروشنده در آن دسته پذیرفته نمی‌شود؛ تجربهٔ عملی توسعه‌دهنده‌ها هم تقریباً همیشه به رد شدن می‌انجامد ([سیاست رسمی](https://support.google.com/googleplay/android-developer/answer/10208820)، [نمونه تجربه](https://www.reddit.com/r/androiddev/comments/1mdtn0s/sms_read_permission/)). همچنین Play Protect برای اپ‌های sideload با `READ_SMS`/`NOTIFICATION_LISTENER` هشدار/بلاک می‌دهد.

**پس سه مسیر انتشار:**

| مسیر | قابلیت بانکی | هزینه/ریسک |
|------|---------------|-------------|
| APK مستقیم (سایت/لینک) | کامل | هشدار Play Protect، به‌روزرسانی دستی، اعتماد کاربر |
| بازار ایرانی (کافه‌بازار/مایکت) | کامل | نیاز به حساب توسعه‌دهندهٔ ایرانی؛ سیاست‌های خودشان |
| Google Play | فقط بدون پیامک | باید بدون SMS منتشر شوید (نسخهٔ Lite) |

**طراحی توصیه‌شده برای استخراج مبلغ (پارسر):**

1. نرمال‌سازی: تبدیل ارقام فارسی/عربی به لاتین، حذف نیم‌فاصله، یکسان‌سازی «ي/ك»، حذف `,` و `.` هزارگان.
2. تشخیص بانک از شمارهٔ فرستنده (الگوهای قابل‌ویرایش در دیتابیس، نه hard-code).
3. تشخیص نوع: فقط **واریز/افزایش موجودی** (کلمات: واریز، به حساب، افزایش موجودی، انتقال، پایا، ساتنا، کارت‌به‌کارت)؛ «برداشت، خرید، کاهش موجودی» رد شود. پیامک‌های `رمز پویا/OTP` هم رد شوند.
4. استخراج: مبلغ، شمارهٔ کارت/حساب مقصد (۴ رقم آخر)، مانده، تاریخ/ساعت، شمارهٔ پیگیری.
5. اعتبارسنجی متقابل با «مانده»: اگر مانده قبل و بعد در پیام هست، اختلاف باید با مبلغ بخواند (کاهش false-positive).
6. **ایمنی از تقلب:** پیامک بانکی قابل جعل است (اپ‌های SMS Spoofing / ارسال با شمارهٔ بانک). هرگز فقط با پیامک، اکانت را تمدید نکنید؛ گزینه‌های ایمن‌تر: تأیید دستی برای مبالغ بالا، تطبیق با شمارهٔ پیگیری، یا کوئری موجودی/صورت‌حساب از درگاه بانک اگر دارید.

**الگوریتم تطبیق (پیشنهاد):**

```
onCreditSms(parsed):
  if exists(hash(sender, body, timestamp)): drop           # ضد تکرار
  if amount <= 0 or not isCredit(parsed): drop
  candidates = open_invoices where remaining_amount == amount
                                       and customer_last4_card == parsed.last4
  if candidates.size == 1: auto_settle(candidate)          # خودکار
  else:
      candidates2 = open_invoices where remaining_amount == amount
      if candidates2.size == 1: suggest(candidate2)        # پیشنهاد، تأیید کاربر
      else: queue_unmatched(parsed)                        # صف «در انتظار تطبیق»
  ledger: entry(customer, credit, amount, ref=sms_hash)
  # مبلغ بیش از فاکتور → باقی به کیف پول/اعتبار مشتری، نه گم شود
```

قواعد مهم دیگر: تطبیق FIFO بدهی‌های قدیمی، پشتیبانی پرداخت چندفاکتوری، پیامک «برگشت/کنسلی» → ثبت معکوس، و **هرگز حذف** پیامک خام (جدول `bank_sms` برای رفع اختلاف).

**جایگزین‌های کم‌ریسک‌تر که در ایران جواب می‌دهند:** خواندن Notification (اگر اپ بانک نوتیفیکیشن واریز بدهد؛ بدون مجوز SMS و سبک‌تر از نظر Play، اما وابسته به اپ بانک)، ارسال پیامک به یک سرور با شمارهٔ اختصاصی (کاربر پیامک واریز را forward می‌کند)، یا تطبیق دستی سریع با جست‌وجوی مبلغ/۴ رقم کارت (۸۰٪ ارزش با ۵٪ هزینه).

### ۳٫۶ دفتر حساب مشتریان بدهکار

- صفحهٔ مشتری: مانده، بدهی سررسیدگذشته، تاریخچهٔ فاکتور/پرداخت/پیامک‌های تطبیق‌داده‌شده، اکانت‌های پنل و وضعیتشان.
- گزارش سنی بدهی (Aging: ۰–۳۰، ۳۱–۶۰، ۶۱–۹۰، +۹۰) + «سقف اعتبار» و «قفل فروش به بدهکار» — این دو ویژگی در عمل از همه چیز بیشتر جلوی ضرر را می‌گیرد.
- یادآوری خودکار بدهی با پیامک (الگوی جدا).

### ۳٫۷ گزارش‌های جامع

نمونهٔ مجموعهٔ گزارش‌های ارزشمند (همه با فیلتر بازهٔ شمسی، پنل، نماینده، بسته):

- فروش: درآمد روزانه/ماهانه، به تفکیک بسته/پنل/نماینده، مقایسهٔ ماه.
- وصول: نقدی/کارت‌به‌کارت/پیامکی، نرخ تطبیق خودکار، صف ناموفق.
- عملیاتی: اکانت‌های فعال/منقضی/تمام‌حجم، تمدیدهای نزدیک (۷ روز)، نرخ تمدید (Churn)، مصرف پهنای‌باند به‌ازای مشتری (از پنل).
- مالی: سود و زیان (درآمد − هزینهٔ سرور/پهنای‌باند/پیامک)، بدهکاران، سنی بدهی.
- خروجی: PDF فارسی با فونت embed شده، Excel/CSV، و اشتراک‌گذاری تصویر خلاصه در واتساپ/تلگرام.
- داشبورد: ۴ عدد کلیدی (درآمد ماه، بدهی کل، اکانت‌های فعال، اکانت‌های ۳ روز آینده منقضی).

## ۴) معماری پیشنهادی

### ۴٫۱ گزینه A — «موبایل‌محور» (ساده، سریع، ارزان) — پیشنهاد برای فاز ۱

```
┌─────────────────────── Android App (Kotlin + Compose) ───────────────────────┐
│ UI (RTL/Jalali) → ViewModel/UseCase → Repository                              │
│   ├─ Room (دفتر، فاکتور، مشتری، پیامک، Outbox)   ← منبع حقیقت (offline-first) │
│   ├─ PanelClient (Retrofit/OkHttp)  → Hiddify 14 API v2                       │
│   ├─ SmsGateway (Kavenegar/SMS.ir)  → ارسال فاکتور/یادآوری                    │
│   └─ BankSmsReceiver (نصب مستقیم)   → پارسر + موتور تطبیق                     │
│ WorkManager: Outbox/Retry/Reconciliation/گزارش‌های شبانه                      │
└──────────────────────────────────────────────────────────────────────────────┘
```

مزیت: بدون هزینهٔ سرور، سریع‌ترین مسیر به محصول. عیب: کلید پنل روی دستگاه، بدون همگام‌سازی چند دستگاه، پیامک فقط تا وقتی اپ زنده/نصب است.

### ۴٫۲ گزینه B — «موبایل + بک‌اند» — پیشنهاد برای محصول واقعی/تیمی

```
Android ←→ Backend (Ktor/Node + Postgres)  ←→ Hiddify API v2 (کلید پنل فقط اینجا)
    ↑            ├─ موتور تطبیق پرداخت (قابل اجرا روی پیامک‌های ارسالی دستگاه)
  پیامک بانکی     ├─ صف پیامک + پنل پیامکی + وب‌هوک تحویل
  (محلی خوانده     ├─ تولید PDF/Excel و لینک اشتراک‌گذاری
   و به بک‌اند     └─ چند ادمین/چند دستگاه، نقش‌ها، لاگ حسابرسی
   ارسال می‌شود)
```

مزیت: امنیت، چند دستگاه، وب‌داشبورد، عدم وابستگی به روشن بودن موبایل. توصیه: **فاز ۱ با A شروع شود، داده و API طوری طراحی شود که مهاجرت به B بدون بازنویسی باشد** (Repository/UseCase، DTO مشترک، کلید Idempotency).

### ۴٫۳ استک پیشنهادی اندروید

| لایه | انتخاب |
|------|--------|
| زبان/UI | Kotlin 2.x، Jetpack Compose، Material 3 |
| معماری | MVVM + Clean (Repository/UseCase)، ماژول‌بندی `:core`, `:data`, `:panel`, `:accounting`, `:sms`, `:feature-*` |
| DB | Room + SQLCipher (رمزنگاری) + migrations تست‌شده |
| شبکه | Retrofit + OkHttp + kotlinx.serialization، Interceptor برای کلید، Timeout کوتاه + Retry با backoff |
| DI | Hilt |
| پس‌زمینه | WorkManager (Outbox، تطبیق، گزارش) |
| امنیت | EncryptedSharedPreferences/Keystore، قفل بیومتریک، مخفی‌سازی صفحه در Recents، ProGuard/R8، عدم لاگ کلید |
| تاریخ | `java.time` + مبدل جلالی (کتابخانهٔ `persian-date`/`jalali` یا پیاده‌سازی خودتان با تست) |
| PDF/Excel | اندروید `PdfDocument` + فونت فارسی embed؛ Apache POI یا خروجی CSV برای Excel |
| تست | JUnit + Turbine + MockWebServer (قرارداد API پنل) + Room migration test + Compose UI test |

## ۶) امنیت، انطباق و توزیع

1. **کلید API پنل = قدرت کامل روی پنل.** روی دستگاه باید رمز شود (Keystore)، در لاگ/کرش‌ریپورت نرود، و در صورت پشتیبانی از چند کاربر، در بک‌اند بماند. از ادمین با نقش محدود (agent) که فقط کاربران خودش را می‌بیند استفاده کنید، نه super admin.
2. **قفل اپ** (PIN/بیومتریک) و **پاک‌سازی خودکار** پس از N تلاش ناموفق، به‌خاطر داده‌های مالی و پیامک‌ها.
3. **حریم خصوصی:** اپ نباید پیامک غیربانکی را ذخیره/ارسال کند؛ فیلتر سخت‌گیرانه بر اساس فرستنده و الگو، عدم آپلود متن کامل، سیاست حریم خصوصی شفاف، و «حذف داده» در تنظیمات. این هم اخلاقی است، هم در بازبینی هر مارکتی امتیاز مثبت.
4. **Google Play:** نسخهٔ Play را بدون مجوز SMS و بدون قابلیت تطبیق خودکار منتشر کنید (نسخهٔ Lite؛ حتی می‌توانید `uses-feature`/فلگ build برای دو flavor بسازید). نسخهٔ کامل را از سایت/بازارهای ایرانی توزیع کنید (با امضای جداگانه و به‌روزرسانی درون‌برنامه‌ای).
5. **قانونی/کسب‌وکاری:** فروش سرویس عبور از فیلترینگ در ایران ریسک حقوقی دارد؛ و برای پیامک انبوه نیاز به خط خدماتی و الگوی تأییدشده است. همچنین نگهداری سوابق مالی مشتریان، تعهدات حریم خصوصی ایجاد می‌کند. (این بخش مشاورهٔ حقوقی نیست.)
6. **پشتیبان‌گیری:** خروجی رمزنگاری‌شدهٔ کامل دیتابیس (فایل) + بازیابی؛ بدون این، یک گوشی گم‌شده = کل دفتر از دست رفته.

## ۹) پرسش‌های باز (پیش از کدنویسی پاسخ دهید)

1. **تک‌کاربره روی یک گوشی** یا **چند نماینده با بک‌اند مشترک**؟ (تفاوت بزرگ در معماری و هزینه)
2. انتشار روی **Play** هم هدف است یا فقط بازار ایرانی/APK؟ (تعیین‌کنندهٔ سرنوشت قابلیت ۵)
3. کدام **پنل پیامکی** استفاده می‌شود؟ آیا خط خدماتی و الگوی فاکتور دارید؟
4. واحد پول پیش‌فرض **تومان یا ریال**، و آیا چند ارزی لازم است؟
5. پیامک بانکی از **چند بانک** باید پشتیبانی شود و آیا نمونهٔ متن‌ها را می‌توانید بدهید؟ (کیفیت پارسر مستقیماً به نمونه‌ها وابسته است)
6. آیا نیاز به **کیف پول/اعتبار مشتری** و **قسط/سررسید** دارید؟
7. آیا از پنل‌های دیگری (مرزبان، 3x-ui) هم پشتیبانی لازم است یا فقط هیدی‌فای ۱۴؟

## ۱۰) جمع‌بندی نهایی

- **شدنی است، و ریسک فنی‌اش پایین است** — به‌جز قابلیت پیامک بانکی که فنی است ولی از نظر توزیع در Play محدود است.
- **هستهٔ ارزش** (حساب‌دفتری + ساخت/تمدید یک‌کلیکی + فاکتور و پیامک + گزارش بدهکاران) در ۷–۸ هفته قابل عرضه است و مستقل از قابلیت پیامک بانکی درآمدزا است. توصیهٔ من: **اول همین را بسازید**، بعد تطبیق پیامک بانکی را به‌عنوان «نسخهٔ Pro» اضافه کنید.
- سه چیز را از روز اول درست بسازید، وگرنه بعداً گران است: (۱) مبلغ `Long` + دفتر ثبت‌محور و تغییرناپذیر، (۲) Idempotency + reconciliation برای عملیات پنل، (۳) لایهٔ Adapter نسخهٔ پنل.
