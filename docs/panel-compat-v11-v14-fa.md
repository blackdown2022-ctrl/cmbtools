## ۱) چیزهایی که در هر چهار نسخه یکسان است

- آدرس API ادمین: `https://<host>/<proxy_path_admin>/api/v2/admin/…`
- احراز هویت: هدر **`Hiddify-API-Key`** با مقدار **UUID ادمین** (`auth.py`).
- `GET  /api/v2/admin/me/` → اطلاعات ادمین (شامل `uuid`) — در هر چهار نسخه هست.
- `GET  /api/v2/panel/info/` → `{"version": "…"}`.
- `GET/POST  /api/v2/admin/user/` و `PATCH/DELETE /api/v2/admin/user/<uuid>/` → **مسیر کلاسیک کاربران**؛ در هر چهار نسخه هست.
- `GET  /api/v2/admin/all-configs/` (فقط ادمین کل) → در پاسخ `proxy_path_client` و `api_path` هست.
- `proxy_path_admin` و `proxy_path_client` **دو رشتهٔ تصادفی جدا** هستند و هنگام نصب جدا ساخته می‌شوند
  (`panel/init_db.py`: `add_config_if_not_exist(ConfigEnum.proxy_path_admin, random)` و همین برای `proxy_path_client`).
  یعنی **پنل ادمین و لینک اشتراک همیشه دو مسیر متفاوت‌اند.**

## ۲) تفاوت نسخه‌ها (چیزی که ۴۰۴ می‌ساخت)

| قابلیت | ۱۱ | ۱۲ | ۱۳ | ۱۴ |
|--------|:--:|:--:|:--:|:--:|
| `GET /api/v2/admin/users/` (صفحهٔ کاربران) | ✗ | ✗ | ✗ | ✅ |
| `POST /api/v2/admin/users/` | ✗ | ✗ | ✗ | ✅ |
| `PATCH/DELETE /api/v2/admin/users/<uuid>/` | ✗ | ✗ | ✗ | ✅ |
| `POST /api/v2/admin/users/bulk/` | ✗ | ✗ | ✗ | ✅ |
| `GET/POST /api/v2/admin/user/` (کلاسیک) | ✅ | ✅ | ✅ | ✅ |
| `PATCH/DELETE /api/v2/admin/user/<uuid>/` | ✅ | ✅ | ✅ | ✅ |
| متای `link_domains` / `can_add` / `read_only` | ✗ | ✗ | ✗ | ✅ |
| فیلدهای `expire_date` / `remaining_days` / `status` | ✗ | ✗ | ✗ | ✅ |
| `GET/POST/DELETE /api/v1/user/` (فقط ادمین کل) | ✅ | ✅ | ✅ | ✅ |

**نتیجهٔ مهم:** اپ نباید به `/api/v2/admin/users/` قفل شود؛ در نسخه‌های ۱۱ تا ۱۳ این مسیر
وجود ندارد و پاسخ **۴۰۴** می‌دهد. همین یک مورد می‌تواند تمام «ساخت کاربر» را بشکند.
اپ از نسخهٔ ۰.۳.۲ به بعد سه سبک را به‌ترتیب امتحان می‌کند و سبکی که جواب داد را ذخیره می‌کند:

```
PAGE   → /api/v2/admin/users/        (۱۴)
LEGACY → /api/v2/admin/user/         (۱۱ تا ۱۴)   ← پیش‌فرض مطمئن
V1     → /api/v1/user/               (۱۰ تا ۱۴، فقط ادمین کل)
```

## ۳) معنی دقیق کدهای وضعیت (کلید رفع ابهام «۴۰۴»)

| پاسخ | معنی در هیدی‌فای | کاری که اپ می‌کند |
|------|------------------|-------------------|
| `200` + JSON | همه‌چیز درست | ادامه می‌دهد |
| **`400 invalid request`** | مسیر پروکسی، «مسیر ادمین» نیست (اعتبارسنجی `proxy_path_validator`) | فوراً می‌ایستد و می‌گوید «مسیر ادمین اشتباه است» |
| **`403 Unathorized`** | مسیر درست است، **کلید API** معتبر نیست (`redirect_to_login()` → چون API است، ۴۰۳ JSON) | می‌گوید «کلید را اصلاح کنید» |
| **`404`** | این مسیر در این نسخه وجود ندارد، **یا** آدرس تکهٔ اضافه دارد | سبک بعدی را امتحان می‌کند |
| `404 "You have no user"` | ادمین هنوز هیچ کاربری ندارد | «فهرست خالی»، نه خطا |
| `405` | این عمل در این مسیر پشتیبانی نمی‌شود | سبک بعدی |
| HTML | به صفحهٔ ورود ریدایرکت شده‌ایم (کلید/مسیر غلط) | خطای صریح |
| 5xx | خطای سرور پنل | متن خطای پنل نمایش داده می‌شود |

## ۴) چرا آدرس‌ها ۴۰۴ می‌گرفتند — سه علت واقعی

### الف) تکه‌های اضافه در آدرس
در هر چهار نسخه، تابع `get_proxy_path_from_url` **فقط تکهٔ اول** مسیر را می‌خواند:

```python
def get_proxy_path_from_url(url: str) -> str | None:
    url_path = urlparse(url).path
    proxy_path = url_path.lstrip("/").split("/")[0] or None
```

پس اگر اپ آدرس را با تکهٔ دوم بفرستد (مثلاً `AbCdEf12/admin` که در نسخهٔ ۰.۳.۰ ذخیره می‌شد)،
مسیر Flask دیگر تطبیق نمی‌خورد و **۴۰۴** برمی‌گردد — بدون هیچ پیام دیگری. در ۰.۳.۲ مسیر
همیشه به **یک تکه** کاهش می‌یابد (پشتیبانی از `…/admin/`، `…/admin/#/users`، `…/api/v2/…` و
حتی لینک اشتراکِ چسبانده‌شده `…/<client_path>/<uuid>/`).

### ب) انتخاب مسیری که در آن نسخه وجود ندارد
`/api/v2/admin/users/` در ۱۱ تا ۱۳ نیست → ۴۰۴. اپ حالا سه سبک را امتحان می‌کند (بند ۲).

### ج) مسیر ادمین با مسیر اشتراک اشتباه می‌شد
`proxy_path_admin` و `proxy_path_client` دو مقدار تصادفی جدا هستند. اگر آدرس پنل کاربر
(یا لینک اشتراک) در فیلد «آدرس پنل» گذاشته شود، پنل **۴۰۰ invalid request** می‌دهد و
اپ حالا دقیقاً همین را توضیح می‌دهد (قبلاً به‌شکل مبهم «۰ کاربر» یا ۴۰۴ دیده می‌شد).

### د) پنهان‌شدن خطا در نسخهٔ قبل
در ۰.۳.۱ کد، ۴۰۴ مسیر کلاسیک را «فهرست خالی» تفسیر می‌کرد؛ بنابراین اپ می‌گفت
«متصل، ۰ کاربر» و مشکل واقعی دیده نمی‌شد. در ۰.۳.۲ فقط پیام `"You have no user"`
«خالی» تلقی می‌شود و بقیهٔ ۴۰۴ها خطای واقعی‌اند.

## ۵) بدنهٔ درخواست ساخت کاربر در هر سبک

```jsonc
// PAGE  (نسخهٔ ۱۴ — POST /api/v2/admin/users/)
{ "uuid": "…", "name": "…", "usage_limit_GB": 30, "package_days": 30,
  "mode": "no_reset", "comment": "09…", "enable": true }

// LEGACY (۱۱ تا ۱۴ — POST /api/v2/admin/user/)
// همان بدنه؛ اسکیمای نسخه‌های قدیمی همین فیلدها را می‌شناسد (uuid لازم نیست ولی مجاز است)

// V1 (۱۰ تا ۱۴ — POST /api/v1/user/)
// uuid اجباری است؛ پاسخ کاربر را برنمی‌گرداند ({status, msg}) → اپ خودش کاربر را می‌خواند
```

## ۶) تمدید در هر نسخه

| نسخه | روش درست |
|------|-----------|
| ۱۴ (`/users/`) | `PATCH` با پرچم‌های `reset_usage=true`، `reset_days=true` (فیلدهای `current_usage_GB`/`start_date` را نمی‌خواند) |
| ۱۴ (`/user/` کلاسیک) | `User.add_or_update` → `start_date=null` و `current_usage_GB=0` را مستقیم می‌پذیرد |
| ۱۱ تا ۱۳ | `start_date=null` + `current_usage_GB=0` + `usage_limit_GB` + `package_days` |

اپ هر دو گروه فیلد را در **یک بدنه** می‌فرستد تا در همهٔ نسخه‌ها درست کار کند
(پرچم‌های `reset_*` فقط برای مسیر `PAGE` نسخهٔ ۱۴؛ برای ۱۱–۱۳ همان `start_date=null`
و `current_usage_GB=0` کافی است).

### معنای «تمدید» در این اپ (از ۰.۴.۰)

تمدید = **ریست کردن روز و حجم**، نه فقط جلو بردن تاریخ. هر کاربری در پنل که
روز و حجمش از نو تنظیم شود، تمدیدشده حساب می‌شود. `PanelSyncRules.isRenewal`
این نشانه‌ها را می‌بیند:

| نشانه در پنل | معنی |
|---|---|
| `start_date` از یک تاریخ به `null` برگشت | شمارش روز از نو (همان دکمهٔ تمدید) |
| تاریخ شروع دوره جلو رفت | تمدید با تاریخ جدید |
| تاریخ انقضا بیش از ۱ روز جلو رفت | روزهای بیشتر |
| مصرف صفر شد **و** روز/بسته هم عوض شد | ریست هم‌زمان حجم و روز |

«بستهٔ شروع‌نشده» (start_date خالی در ۱۱–۱۳): تاریخ انقضا فقط پیش‌بینی روزانه است
و هر روز یک روز جلو می‌رود؛ در این حالت به تاریخ تکیه نمی‌شود و فقط تغییر خودِ بسته
(روز/حجم) تمدید شمرده می‌شود تا فاکتور الکی صادر نشود.

در اپ، دکمهٔ **تمدید** در کارت هر اکانت (تب «پنل» در پروفایل مشتری) و دکمهٔ بالای صفحه
همین کار را انجام می‌دهد: مصرف صفر، `start_date` پاک، سقف حجم و روز برابر بستهٔ جدید،
فاکتور تمدید + پیامک اختیاری.

## ۷) لینک اشتراک

در هر چهار نسخه: `https://<domain>/<proxy_path_client>/<user_uuid>/`
(`panel/hiddify.py` → `get_account_panel_link`).

پیدا کردن `proxy_path_client`:

1. اگر کاربر خودش «پایهٔ لینک اشتراک» را وارد کرده باشد → همان.
2. نسخهٔ ۱۴ → `link_domains[0].base` در پاسخ `GET /api/v2/admin/users/`.
3. هر نسخه‌ای که کلیدش **ادمین کل** باشد → `GET /api/v2/admin/all-configs/` و خواندن `proxy_path_client`.
4. در غیر این صورت → فیلد دستی در تنظیمات (اپ راهنمایی می‌کند).

## ۸) چه چیزی در اپ ۰.۳.۲ اضافه شد

- موتور تشخیص نسخه: `PAGE` → `LEGACY` → `V1`، با ذخیرهٔ سبکِ موفق در `panel_configs.apiFlavor`.
- نمایش **جدول کاوش** در تنظیمات: هر آدرس + کد وضعیت + معنی (دکمهٔ «جستجوی خودکار مسیر و نسخه»).
- `PanelTarget`/`PanelHttp` جای Retrofit: آدرس‌ها دستی ساخته می‌شوند (بدون کدگذاری `%2F` که ۴۰۴ می‌ساخت)
  و متن خام پاسخ همیشه در دسترس است.
- محاسبهٔ تاریخ انقضا و وضعیت برای نسخه‌های ۱۱–۱۳ که این فیلدها را ندارند.
- User-Agent معمولی مرورگر تا WAF/Cloudflare درخواست را ۴۰۳/۴۰۴ نکند.
- «تست ساخت کاربر» (ساخت و حذف یک کاربر موقت) و گزارش قابل‌کپی با همهٔ آدرس‌ها.

## ۹) یافته‌های ۰.۳.۳ — گزارش پنل واقعی (`11.0.13`)

گزارش واقعی از پنل `srv1.tiznet.site` (هیدی‌فای **۱۱.۰.۱۳**) این چیزها را روشن کرد:

### الف) «۴۰۴» در گزارش به‌شکل **۵۰۰** ظاهر می‌شود
در نسخه‌های ۱۱–۱۳ فایل `hiddifypanel/panel/common.py` این را دارد:

```python
@app.errorhandler(Exception)
def internal_server_error(e):
    ...
    if hutils.flask.is_api_call(request.path):
        return jsonify({'msg': str(e)}), 500
```

یعنی هر مسیر ناشناخته‌ای در API، **کد ۵۰۰** با بدنهٔ
`{"msg":"404 Not Found: The requested URL was not found on the server..."}` برمی‌گرداند.
بنابراین «این مسیر در این نسخه نیست» را نمی‌شود فقط با «کد == ۴۰۴» تشخیص داد.

از ۰.۳.۳ این حالت با `HttpResult.isMissingRoute` شناخته می‌شود و در گزارش
با علامت ▫️ (خطا نیست) نشان داده می‌شود، نه ❌.

### ب) مسیر درست در ۱۱.۰.۱۳ فقط `/api/v2/admin/user/` است
`GET /api/v2/admin/me/` → ۲۰۰، `GET /api/v2/panel/info/` → `version: "11.0.13"`،
`GET /api/v2/admin/users/` → ۵۰۰/۴۰۴ (وجود ندارد)، `GET /api/v2/admin/user/` → فهرست.

### ج) فهرست خالی یعنی **صفر کاربر**، نه خطا
`UsersApi.get` در `users_api.py`:
```python
users = User.query.filter(User.added_by.in_(g.account.recursive_sub_admins_ids())).all() \
        or abort(404, "You have no user")
```
`recursive_sub_admins_ids()` خودِ ادمین و زیرمجموعه‌هایش را برمی‌گرداند؛ پس ادمین کل
همهٔ کاربران را می‌بیند. اگر با کلید یک ادمین جزئی وارد شوید، فقط کاربرانِ او را می‌بینید.
از ۰.۳.۳ «سطح دسترسی کلید» (`super_admin` / `admin` / `agent`) در گزارش نشان داده می‌شود.

### د) باگ تمدید: `start_date: null` هرگز فرستاده نمی‌شد
`Json { explicitNulls = false }` مقدار `JsonNull` را از بدنهٔ درخواست **حذف** می‌کرد؛
یعنی تمدید فقط `package_days` را عوض می‌کرد و تاریخ شروع قبلی سر جایش می‌ماند
⇒ کاربر عملاً تمدید نمی‌شد. حالا بدنه‌ها با `JsonObject.toString()` ساخته می‌شوند (تنظیمات پیش‌فرض
کتابخانه ⇒ `explicitNulls = true`) و `"start_date": null` واقعاً ارسال می‌شود.

### ه) باگ تمدید: فیلدهای ناشناخته ⇒ ۴۲۲
اسکیمای PATCH در ۱۱–۱۳ (`PatchUserSchema` در `schema.py`) فیلدهای
`reset_usage` / `reset_days` را ندارد و marshmallow (که apiflask مستقیم از آن ارث می‌برد،
بدون `Meta.unknown = INCLUDE`) با **۴۲۲ «Unknown field.»** رد می‌کند.
از ۰.۳.۳ این دو فیلد فقط برای سبک `PAGE` (نسخهٔ ۱۴) فرستاده می‌شوند و در صورت
دریافت ۴۲۲ یک بار بدون آن‌ها تلاش دوباره می‌شود.

### و) بستهٔ شروع‌نشده (`start_date = null`)
طبق `User.remaining_days` در `models/user.py` نسخهٔ ۱۱:
```python
elif self.start_date: res = self.package_days - (today - self.start_date).days
else:             res = self.package_days      # هنوز شروع نشده
```
اپ هم از ۰.۳.۳ همین را تقلید می‌کند: `remainingDaysOrComputed = packageDays` و
انقضای «پیش‌بینی» = امروز + روزهای بسته. برای جلوگیری از فاکتور الکیِ تمدید،
تا زمانی که بسته شروع نشده (`notStarted`) تمدید تشخیص داده نمی‌شود.
