# بررسی عدم تأیید واریز و تغییرات تب ربات — نسخهٔ ۰.۷.۰

## نتیجهٔ بررسی علت احتمالی

«آزمایش اتصال موفق» فقط پاسخ `GET /health` و Secret را بررسی می‌کند؛ این آزمون به‌تنهایی ثابت نمی‌کند پیامک دریافت شده، ارسال واریز روشن است، یا مبلغ سفارش با پیامک تطبیق دارد. گزینهٔ ارسال پیامک خاموشِ پیش‌فرض و مستقل است و مجوز `RECEIVE_SMS` هم باید در Android داده شده باشد.

در نسخهٔ قبلی، SMS فقط وقتی به API می‌رفت که parser هم‌زمان واریز اعتباری تشخیص دهد، بانک را از شناسهٔ فرستنده بشناسد، مبلغ مثبت/قابل‌تبدیل داشته باشد و کد پیگیری را با regex پیدا کند. برای نمونه، فرستندهٔ بانکیِ ناشناخته یا قالب کد پیگیریِ متفاوت باعث می‌شد اصلاً درخواست پرداخت به سرور نرسد، حتی اگر health موفق بود. اگر درخواست می‌رسید، mismatch مبلغ، بیش از یک سفارش با مبلغ یکسان، یا بسته/منقضی‌شدن سفارش می‌توانست باعث رد دقیق سمت سرور شود.

از این مخزن به‌تنهایی نمی‌شود علت همان پرداخت قبلی را قطعی تعیین کرد: متن واقعی SMS و نتیجهٔ درخواست/رویداد سرور در دسترس این بررسی نیست. نسخهٔ جدید برای دفعات بعد، در تب «وضعیت» نتیجهٔ آخرین parse/ارسال، مبلغ ریالی خوانده‌شده و مبلغ تومانی‌ای را که اپ محاسبه می‌کند، کد HTTP و پاسخ خطای ربات نگه می‌دارد؛ تب «آزمایش» نیز آخرین SMSهای ذخیره‌شده را بدون ارسال مجدد نشان می‌دهد. اگر درخواست به سرور رسیده باشد، بخش رویدادهای بانکی ربات هم باید خطای مبلغ مبهم یا بدون سفارش را ثبت کرده/به مدیر هشدار داده باشد.

## تغییر رابط و بررسی سفارش

- تب اصلی «ربات» به نوار پایین اضافه شد و میان‌بر قبلی آن از داشبورد حذف شد.
- داخل بخش ربات، سربرگ‌های «وضعیت»، «سفارش»، «آزمایش» و «تنظیمات» جدا هستند.
- endpoint مستند `GET /wp-json/webdide-cv/v1/status?order_id=...` در اپ استفاده می‌شود تا وضعیت و مبلغ یک سفارش مشخص را از سرور بخواند.
- API عمومی Shetab این پروژه endpoint فهرست‌کردن همهٔ سفارش‌ها با Secret اپ ندارد؛ برای همین UI شناسهٔ یک سفارش را می‌گیرد و فهرست کامل جعل نمی‌کند یا از API مدیریتی Mini App بدون نشست تلگرام استفاده نمی‌کند.
- صفحهٔ وضعیت، مجوز SMS را از تست health جدا نشان می‌دهد.

## اصلاح بازگشت اندروید

تغییر بین تب‌های اصلی با stack محدود انجام می‌شود. کلید Back در تب اصلی غیر از داشبورد به داشبورد برمی‌گردد و entryهای تب‌های قبلی را پاک می‌کند؛ در صفحه‌های جزئی فقط یک سطح pop می‌شود. هدف، جلوگیری از باقی‌ماندن چند تب/صفحهٔ اصلی در stack و تکرار آن‌ها با Back است.

## قرارداد و ایمنی

سرور هنوز فقط مبلغ یکتا و `recipeId` را تطبیق می‌دهد؛ شمارهٔ کارت مقصد را از اپ دریافت نمی‌کند و بانک را مستقل استعلام نمی‌کند. تب «سفارش» فقط وضعیت همان ID را می‌خواند. ارسال SMS همچنان خاموش پیش‌فرض، HTTPS-only و محدود به پیامک‌های واجدشرایط باقی می‌ماند.
